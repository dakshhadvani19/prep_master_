# PrepMaster Primary Key Rules

**Purpose:** Keep the primary-key conventions consistent when adding or restoring catalog rows and when designing future Supabase tables.

**Baseline reviewed:** 2026-10-25 against the live Supabase project `llqwtgwjlwgrftihtern`, the current repository `main` branch, and the current syllabus/mapping data files. Re-check the live schema before any future migration; this document records observed rules and should be updated when the design changes.

## 1. Current primary-key strategies

A primary key is not generated the same way for every table. Follow the specific table contract below rather than assuming every ID is an auto-incrementing number.

| Live table | Primary key | Live PostgreSQL definition | Rule |
| --- | --- | --- | --- |
| `public."Courses"` | `CourseId` | `BIGINT` identity, `GENERATED BY DEFAULT` | Supabase/PostgreSQL generates a value when omitted. Existing CourseIds are stable and are used as the prefix when computing catalog SubjectIds. |
| `public."Subjects"` | `SubjectId` | `BIGINT` identity, `GENERATED BY DEFAULT` | Existing catalog rows use explicit, encoded SubjectId values. For catalog syncs, calculate and supply the canonical ID; do **not** let the identity sequence create an unrelated value. |
| `public."Students"` | `StudentId` | `BIGINT` identity, `GENERATED BY DEFAULT` | Database-generated profile ID. `auth_uid` is a separate UUID FK/unique identity anchor; do not substitute it for StudentId. |
| `public."Admins"` | `AdminId` | `BIGINT` identity, `GENERATED BY DEFAULT` | Database-generated admin profile ID. `auth_uid` is a separate UUID FK/unique identity anchor. |
| `public."Feedbacks"` | `FeedbackId` | `BIGINT` identity, `GENERATED BY DEFAULT` | Database-generated feedback ID. `StudentId` is a separate FK to `Students.StudentId`. |
| `public."Leaderboards"` | `LeaderboardId` | `BIGINT`, default expression based on `random()`; not an identity column | Existing schema generates a random bigint by default. Preserve the existing strategy unless a deliberate migration changes it; the primary-key constraint still rejects collisions. |
| `public."TestsData"` | `TestId` | `BIGINT`, no identity and no default | No schema change. A server-side persistence trigger allocates the key under a transaction advisory lock; the browser never supplies `TestId`. Values remain unique. |
| `public."TestAttempts"` | `AttemptId` | `BIGINT` identity, `GENERATED ALWAYS` | Database-generated primary key for each attempt; includes `TestId` and `StudentId` foreign keys. |
| `public."TestRooms"` | `RoomId` | `BIGINT` identity, `GENERATED ALWAYS` | Database-generated room-summary row ID; `TestId` references `TestsData.TestId`. Stores participant IDs, scores/counts and the 2D canonical answer grid; not the Redis join code or live room registry. `RoomId` is not a join code. See [`docs/TEST_ROOMS_SCHEMA_AND_IMPLEMENTATION.md`](./TEST_ROOMS_SCHEMA_AND_IMPLEMENTATION.md). |
| `private.exam_attempts` | `id` | `UUID`, default `gen_random_uuid()` | Durable student exam/Test Room attempt. `user_id` references `auth.users.id`; private `core_test_id`, `core_attempt_id`, and `core_room_id` link to `public.TestsData.TestId`, `public.TestAttempts.AttemptId`, and `public.TestRooms.RoomId`; server-side RPCs are the only application access path. |
| *(retired)* `exam_grades` | — | Removed on 2026-10-27. The authoritative score and total marks remain on `private.exam_attempts`; the separate table was redundant and empty. |
| `private.exam_attempt_keys` | `attempt_id` | `UUID`, PK/FK to `private.exam_attempts.id` | One server-only answer key per attempt. The table is unexposed and browser roles have no schema/table privileges. |
| `private.auth_otp` | `email` | `TEXT` primary key | Short-lived signup challenge storage, accessible only through server-only OTP functions. |

Live verification on 2026-10-27 confirmed that public `TestsData`, `TestAttempts`, and `TestRooms` receive the saved-paper, per-student and per-room mirrors from private operational attempts without structural changes. No live `Subscribers` or `Subscriptions` table was verified in this review. See [`docs/TEST_ROOMS_SCHEMA_AND_IMPLEMENTATION.md`](./TEST_ROOMS_SCHEMA_AND_IMPLEMENTATION.md) for the current contract.

## 2. Canonical SubjectId encoding rule

For catalog subject IDs, use the assigned numeric `CourseId` from the live `public."Courses"` row plus the **verified official subject code** and a two-digit occurrence number.

Conceptually:

```text
SubjectId = CourseId + LPAD(encode(official_subject_code) + occurrence_no, 12, '0')
```

This is string concatenation to build the decimal ID, not numeric addition.

### Encoding steps

1. Start from the official subject code in the authoritative course/syllabus mapping. Do not start from the subject title or infer the code from the semester.
2. Process the code from left to right:
   - Keep numeric digits unchanged.
   - Convert each alphabetic letter to its 1-based alphabet position: A=1, B=2, …, Z=26.
   - Each letter contributes its decimal number without forcing that individual number to two digits (for example, C contributes `3`, M contributes `13`, and Z contributes `26`).
   - Ignore separators such as hyphens or spaces when constructing the encoded numeric string.
3. Append a two-digit occurrence number. Use `01` when this official code appears once in the course. If the same official code occurs more than once in the same course, allocate `01`, `02`, `03`, … to the separate occurrences in a stable, documented order (normally the mapped semester/source order).
4. Left-pad the encoded code plus occurrence number to **12 digits** using zeroes.
5. Prefix the resulting 12 digits with the actual numeric `CourseId` from Supabase.

Keep the result within PostgreSQL `BIGINT` range and check that no existing row already uses it before inserting.

### Verified examples from the live catalog

**Example A — Diploma Computer Engineering, CourseId 44**

The source code `09CE2101` encodes as:

```text
09 + C(3) + E(5) + 2101 = 09352101
append occurrence 01      = 0935210101
left-pad to 12 digits     = 000935210101
prefix CourseId 44        = 44000935210101
```

The live `public."Subjects"` row for CourseId 44 has SubjectId `44000935210101` for **Computer Fundamental Skill**, semester 1. CourseId 44 had 39 live subject rows at this review; the inspected IDs were distinct.

**Example B — repeated official code in CourseId 20 (BBA)**

The code `04SC0002` encodes as `04 + S(19) + C(3) + 0002 = 041930002`. It occurs three times in the live CourseId 20 mapping, in semesters 0, 4, and 6. The occurrence suffix distinguishes those separate course/semester records:

| Semester in current data | SubjectId |
| ---: | ---: |
| 0 | `20004193000201` |
| 4 | `20004193000202` |
| 6 | `20004193000203` |

A second repeated code, `04SC0001`, appears in semesters 4 and 6 as `20004193000101` and `20004193000102`.

### Rules for repeated subjects

- The combination of course, official source code, and occurrence is what disambiguates a repeated code; the human-readable title alone does not.
- The CourseId prefix separates the same encoded source code used by different courses.
- Do not collapse repeated course/semester occurrences just because the source code or title is identical.
- Assign occurrence numbers deterministically. Before insertion, compare against the existing catalog and its source manifest so an update cannot accidentally reassign IDs.
- Once a SubjectId is referenced by another table, a syllabus JSON entry, a bridge map, or exam history, keep it stable. A title correction or semester change is not by itself a reason to regenerate the primary key.
- Never infer Semester from digits embedded in SubjectId; use the live `Subjects.Semester` field and verified source mapping.

## 3. Which files are authoritative for which purpose?

- `global-exam-prep/src/data/universitySyllabus.js`: contains syllabus/question-generation entries keyed by legacy or synthetic identifiers such as `ce101`. Those keys are **not automatically Supabase SubjectIds**, and this file does not itself implement the numeric SubjectId conversion algorithm.
- `global-exam-prep/src/data/mockData.js`: contains legacy/source catalog structures used by the existing exam flow. A source `id` in this file is not automatically the live numeric SubjectId.
- `global-exam-prep/src/data/subjectIdBridge.json`: maps numeric SubjectId keys to legacy/source compatibility data (including source subject ID, source course ID, numeric CourseId, and semester). It is a compatibility bridge, not the authoritative live catalog, and its source ID value must not blindly be treated as the official code used to calculate SubjectId.
- `global-exam-prep/src/data/courseMapping.json`: maps source-course identifiers to numeric CourseIds and provides compatibility metadata.
- `global-exam-prep/src/data/subjectSemesterMap.json`: legacy semester compatibility mapping; it is not the runtime catalog source of truth.
- `Syllabus/syllabus_txt/` generated semester JSON and the official source syllabus/manifest supply the source-code context. When a generated record has both `subject_id` (encoded numeric ID) and `subject_code` (official source code), validate both against the current Supabase row and source manifest. Do not encode an already encoded `subject_id` a second time.
- Live `public."Courses"` and `public."Subjects"` are the database source of truth for currently active catalog records. Check a course and source mapping before using an ID from a static/compatibility file.

The checked-in bridge currently contains more entries than the live Subjects table, so a mapping entry by itself does not prove that the corresponding row is active in Supabase. Removed/inactive course IDs and archived rows must not be reinserted without checking the current catalog and source evidence.

## 4. Foreign-key type and identity rules

- A foreign-key column must use a compatible PostgreSQL type with the referenced key. The current catalog uses `BIGINT` for `Subjects.CourseId → Courses.CourseId`, `Feedbacks.StudentId → Students.StudentId`, and `Leaderboards.SubjectId → Subjects.SubjectId`.
- `Students.auth_uid` and `Admins.auth_uid` refer to Supabase Auth UUIDs; they are not the numeric profile primary keys.
- Do not place identity-generation assumptions into future SQL unless the current contract explicitly calls for them.
- Keep RLS enabled and retain least-privilege grants for exposed tables. Primary-key correctness does not replace access-control rules.

## 5. TestsData TestId rule: SubjectId + test occurrence

`public."TestsData".TestId` is a manually supplied `BIGINT` primary key. It is **not** an identity/auto-increment value. Its value combines the subject's existing numeric `SubjectId` with the occurrence number of one saved test set.

### Construction rule

```text
TestId = decimal-string(SubjectId) + decimal-string(test_occurrence)
```

This is **string concatenation, not arithmetic addition**. Concatenate first, then convert the full decimal string to `BIGINT`.

For example, for SubjectId `44000935310201`, occurrence 25 produces TestId `4400093531020125`.

### Current Semester 1 v2 exam-type ranges

Occurrence is counted **per subject across that subject's exam types**; do not restart at 1 for each exam.

| `isDepartmentalSubject` | Occurrences | Exam type | Variants |
| --- | ---: | --- | ---: |
| `false` | 1–12 | Mid 1 | 4 Easy, 4 Medium, 4 Hard |
| `false` | 13–24 | Mid 2 | 4 Easy, 4 Medium, 4 Hard |
| `false` | 25–36 | ESE | 4 Easy, 4 Medium, 4 Hard |
| `true` | 1–12 | Mid 1 | 4 Easy, 4 Medium, 4 Hard |
| `true` | 13–24 | Mid 2 | 4 Easy, 4 Medium, 4 Hard |
| `true` | — | ESE | Not generated |

These ranges define the current v2 Semester 1 bank; they do not change the general concatenation rule. The exact mapping is stored in `Questions/TestsData/Diploma/Computer Engineering/Semester 1/exam-bank-v2.json` under `test_index`. Do not infer subject, exam type or difficulty by blindly removing the last digit(s), because the occurrence may contain two digits and the table has no metadata columns.

### Rules when generating test IDs

- Start from the **actual, active SubjectId in Supabase**. Do not use a legacy source ID, syllabus filename, or unverified bridge-map entry.
- Follow an explicit occurrence map and inspect existing `TestsData` rows before allocating IDs. Do not assume a number is free based only on in-memory state.
- Do not regenerate a TestId when revising the same test set. Reuse the same ID for that test set; allocate a new occurrence only for a genuinely new test set.
- TestId must be unique across the entire `TestsData` table. If a candidate conflicts with an existing ID, stop and resolve the collision rather than overwriting another test.
- Keep the concatenated result inside PostgreSQL's signed `BIGINT` range (`-9223372036854775808` through `9223372036854775807`).
- Preserve the subject association in a manifest because `TestsData` currently stores no `SubjectId` column. A separate foreign-key column would require a separately approved schema change.

### Relationship to TestAttempts

- `TestsData.TestId` identifies a saved test set, not an individual student attempt.
- If students can attempt a test more than once, `TestAttempts` needs its own per-attempt primary key and a `TestId` foreign key to `TestsData.TestId`.
- The final `TestAttempts` schema must be established against the live database before creating that table.

## 6. Safe insert checklist

1. Read the current live CourseId and confirm the course is active.
2. Verify the authoritative official subject code, title, and semester.
3. Calculate SubjectId using the encoding and occurrence rules above, or use the already verified `subject_id` from the official generated mapping without re-encoding it.
4. Query Supabase for the candidate SubjectId and for existing rows with the same CourseId/source code before insertion.
5. Reuse the existing ID for an existing catalog row; never attempt to insert a duplicate primary key.
6. Keep `subjectIdBridge.json`, `subjectSemesterMap.json`, and any legacy source data synchronized only as compatibility maps, after the live catalog change has been verified.
7. After any schema or catalog change, verify the resulting constraints and rows against Supabase and update this document if the key rules changed.
